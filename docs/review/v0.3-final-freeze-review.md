# SAIF Protocol v0.3 Specification Freeze Review

## Review Status

- **Review target:** Draft PR #2, `Harden SAIF Protocol v0.3 contracts`
- **Head commit:** `4a05e42078d985369d1be37c3177b98772c877df`
- **Base:** `feature/reference-architecture-v03`
- **Review type:** final standards-consistency review before merge
- **Freeze decision:** **NOT READY TO FREEZE**

This review evaluates the public protocol specification only. It does not review
or introduce runtime code, MCP implementation, commercial behavior, payment
logic, or Provider-specific implementation.

## Executive Summary

PR #2 substantially improves the v0.3 architecture. It establishes explicit
contracts for Authorization Decisions, Extension Manifests, state-changing
operations, API operations, and minimum security properties. The Core,
Extension, Storage, API, and Security boundaries are materially clearer than in
the initial architecture draft.

The specification is not yet suitable for a v0.3 freeze. Five blocking
consistency issues remain:

1. schema identity does not identify an immutable protocol version;
2. two incompatible operation-status vocabularies are normative;
3. extension namespace governance is contradictory across specifications;
4. one normative invalid vector uses a non-standard error category; and
5. published vectors do not cover the conformance cases required by the new
   contracts and the v0.3 release criteria.

These findings concern specification consistency and testability. Resolving them
does not require a runtime or a commercial implementation.

## 1. Schema Naming and Version Strategy

### What Is Consistent

- Schema files use lowercase kebab-case names with `.schema.json`.
- All ten schemas declare JSON Schema Draft 2020-12.
- New artifacts use stable object names: `authorization_decision` and
  `extension_manifest`.
- Protocol instance versions use numeric `MAJOR.MINOR.PATCH` without the
  documentation-only `v` prefix.

### Blocking Finding B-01: Canonical Schema Identity Is Not Version-Safe

Every schema `$id` points to an unversioned repository path such as:

```text
https://github.com/songluyi/SAIF-Protocol/schemas/request.schema.json
```

That identifier can resolve to different content after a later protocol release.
It therefore cannot safely act as the canonical identity of an immutable v0.1,
v0.2, or v0.3 schema. The two new schemas contain an instance-level
`saif_version`, but their patterns accept any numeric semantic version. The other
eight schemas do not contain an instance-level version field.

This conflicts with the [Protocol Versioning Strategy](../protocol-versioning.md),
which requires the release tag, documentation, schemas, and examples to identify
the same protocol version before a stable release.

**Interoperability risk:** independent validators may cache or resolve the same
`$id` to different schema content while all believe they are validating the same
protocol version.

**Required freeze action:** define one canonical schema-version strategy and
apply it consistently. A compliant resolution may use versioned `$id` values,
immutable release references, or a versioned schema catalog. The resolution must
state how an instance or negotiated profile selects the applicable schema. This
is an artifact-identity clarification, not a change to business semantics.

## 2. Contract Dependency Consistency

### What Is Consistent

- `CreateRequest` produces only `DRAFT`; `SubmitRequest` performs the transition
  to `SUBMITTED`.
- Authorization evaluation maps `ALLOW`, `DENY`, and `REQUIRES_ACTION` to valid
  Request lifecycle outcomes.
- `ConvertRequest`, `StartExecution`, and `CompleteExecution` respect the
  cross-object lifecycle in the State Model.
- revisions and idempotency are operation metadata, preserving v0.2 object
  schema compatibility.
- Provider results remain subordinate to Core lifecycle validation.

### Blocking Finding B-02: Operation Outcome Vocabularies Conflict

The existing `schemas/common-status.schema.json` describes a provider-neutral
status result for SAIF protocol operations and permits:

```text
SUCCESS, PENDING, FAILURE
```

[Action Execution Semantics](../specs/action-execution-semantics.md) defines the
normative state-changing operation outcomes as:

```text
APPLIED, REPLAYED, PENDING, REJECTED, CONFLICT, FAILED
```

[API Operation Semantics](../specs/api-operation-semantics.md) requires the
second vocabulary in every state-changing result. No dependency rule states
whether Common Status is superseded, mapped, nested, or excluded from the v0.3
Reference Node profile.

**Interoperability risk:** two implementations can return different status
vocabularies for the same operation while each claims conformance.

**Required freeze action:** declare the normative relationship between Common
Status and the v0.3 operation result. If both remain valid, publish a lossless
mapping and identify which field controls protocol semantics.

### Non-Blocking Dependency Clarification

API actor roles include `OWNER`, `AUTHORIZATION_EVALUATOR`, `REFERENCE_NODE`,
and `AUDITOR`, while the Audit Event Model uses `PARTY`, `AGENT`, `PROVIDER`, and
`SYSTEM`. A normative mapping should state, for example, that an Owner is audited
as a Party and system roles are audited as System actors with their resolved
identity. The current distinction is understandable but not explicit.

## 3. Extension Governance Completeness

### What Is Complete

- manifests declare extension identity, version, SAIF compatibility range,
  affected protocol areas, requirement status, schema URI, and digest;
- unknown required extensions fail closed;
- optional extensions may be ignored only when core semantics remain complete;
- duplicate ID/version entries with different digests are rejected;
- standard and private proposal status is distinguished; and
- schema retrieval does not authorize code execution.

### Blocking Finding B-03: Namespace Rules Contradict Each Other

The [Extension Proposal Process](../proposal-process.md) recommends experimental
namespaces such as:

```text
x-organization-capability
```

The [Extension Declaration](../specs/extension-declaration.md) requires a
reverse-domain namespace, and `schemas/extension-manifest.schema.json` rejects
the proposal-process example because the pattern requires dot-separated labels.
The two normative governance documents therefore give incompatible instructions
to extension authors.

There is also an ambiguous invalid vector:
`conformance/invalid/extension-manifest-required-ignore.json` sets `namespace`
equal to `extension_id`. That violates the semantic requirement that
`extension_id` begin with `namespace` followed by `.` while the vector intends to
test only the `required`/`unknown_behavior` combination. A conforming semantic
validator could reject it for either reason.

**Required freeze action:** select one namespace model across the proposal
process, declaration, schema, examples, and vectors. Each invalid vector must
contain one intentional failure or explicitly define error precedence.

### Non-Blocking Extension Recommendations

- Define whether `compatibility.saif_min` must be numerically lower than
  `saif_max_exclusive`; the schema cannot express that comparison by itself.
- Add a media type for the artifact identified by `schema.uri` so exact digest
  verification is unambiguous across schema and non-schema validation artifacts.
- State how a `SUPERSEDED` manifest identifies its successor or rely explicitly
  on the associated SEP document for that relationship.
- Publish a core error-code registry to prevent future SEP code collisions.

## 4. Conformance Vector Coverage

### Blocking Finding B-04: Invalid Error Category

`conformance/invalid/action-stale-revision.json` expects category `STATE`.
The Standard Error Model defines `STATE_TRANSITION` as the normative category and
permits `STATE` only as the shortened token inside an error code such as
`SAIF-STATE-0002`.

**Required freeze action:** use `STATE_TRANSITION` as the vector category while
retaining `SAIF-STATE-0002` as the code.

### Blocking Finding B-05: Required Coverage Is Incomplete

The current suite contains 13 vectors: six valid and seven invalid. Eight target
JSON Schemas and five target semantic specifications. This is useful initial
coverage, but it does not satisfy the MUST-level conformance lists in the five
new contracts or the release criteria in the v0.3 roadmap.

| Contract area | Covered examples | Required cases still missing before freeze |
| --- | --- | --- |
| Authorization Decision | valid `ALLOW`; missing Request revision | `DENY`, `REQUIRES_ACTION`, expiry, revoked Authorization, reference mismatch, cross-Request replay, non-`ALLOW` conversion |
| Extension Declaration | valid optional manifest; required extension rejection; invalid required/ignore combination | valid required manifest, optional unknown ignore, namespace mismatch, incompatible range, digest mismatch, duplicate manifest conflict |
| Action Execution | unchanged replay, stale revision, atomic Request conversion, Provider actor mismatch | changed-input key conflict, concurrent terminal conflict, atomic Execution completion, asynchronous completion, failed atomic recovery, audit de-duplication |
| API Operations | partial coverage through action vectors | allowed/denied actor matrix, each required operation pre/post-state, query authorization, pagination behavior, result/error envelope references |
| Security Profile | revision binding, Provider mismatch, unknown required extension | Owner isolation, idempotency-key conflict, digest mismatch, downgrade rejection, error/audit redaction |
| v0.2 governance dependencies | Request and Order schema cases | Standard Error shape, Audit Event attribution, lifecycle transition matrix, cross-object reference integrity |

The Conformance Specification itself remains titled v0.2 and describes only a
v0.2 conformance claim. It should explicitly define how a v0.3 Reference Node
profile claim selects mandatory v0.3 vectors and reports profile coverage.

**Required freeze action:** publish deterministic valid and invalid vectors for
the missing MUST cases, or explicitly downgrade/defer requirements through the
governance process. Every invalid vector must identify one expected primary
failure and stable Standard Error category/code.

## 5. Security Profile Completeness

### Assessment

The [Security Profile](../specs/security-profile.md) is architecturally complete
enough for a provider-neutral v0.3 draft. It covers:

- trust-zone separation;
- authenticated-peer to protocol-actor mapping;
- separation of authentication and business Authorization;
- decision freshness, revocation, scope, and expiry;
- replay, idempotency, and optimistic-concurrency controls;
- Owner and tenant isolation;
- Provider result attribution;
- extension digest and trust-policy checks;
- downgrade resistance;
- audit integrity, error minimization, and secret exclusion;
- cryptographic agility; and
- resource-exhaustion controls.

No commercial authentication provider, cryptographic product, payment system,
or deployment topology is made normative.

### Freeze Condition

The profile's remaining blocking concern is evidence, not architecture. Its own
mandatory conformance list is not covered by the current vector suite, as shown
in B-05. The profile may be frozen after those observable behaviors have
deterministic vectors or an explicit binding-profile deferral.

### Non-Blocking Security Recommendations

- Define the authoritative time source and permitted clock-skew treatment for
  `evaluated_at` and `expires_at` checks.
- State the minimum audit evidence produced for rejected authentication,
  downgrade, extension-integrity, and Owner-isolation attempts.
- Clarify which public-network requirements are verified by a future transport
  binding profile rather than by core Reference Node vectors.
- Define safe behavior when an extension schema URI is unavailable but a locally
  trusted artifact with the declared digest is present.

## Non-Blocking Recommendations Summary

1. Publish a normative API-role to Audit-actor mapping.
2. Establish a central registry for core Standard Error codes and reason codes.
3. Define clock source and skew behavior for expiring decisions.
4. Add media-type and supersession guidance to Extension Manifests.
5. Separate core Reference Node security evidence from future transport-binding
   security evidence.
6. Add a machine-readable conformance profile manifest in a future proposal so
   required vectors can be selected without repository-specific assumptions.

## v0.3 Freeze Decision

### Decision: NOT READY TO FREEZE

PR #2 should not be merged as the frozen v0.3 specification in its current form.
The architecture and contract direction are suitable, but the five blocking
issues above permit incompatible implementations or make conformance claims
non-deterministic.

### Conditions for Re-Review

The freeze review may be repeated after:

1. canonical schema version identity is defined;
2. operation status vocabularies are reconciled;
3. extension namespace governance and the ambiguous vector are aligned;
4. the stale-revision vector uses the normative error category; and
5. the mandatory v0.3 conformance matrix is covered or explicitly deferred.

After those changes, the repository should rerun JSON parsing, Draft 2020-12
schema validation, valid/invalid vector evaluation, Markdown validation, and a
cross-document terminology check. If all gates pass and no new normative
contradiction appears, v0.3 can move to **FREEZE APPROVED** without requiring a
runtime implementation.
