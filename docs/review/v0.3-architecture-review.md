## Executive Assessment

Draft PR #1 is a strong conceptual foundation. It correctly treats the Reference Node as a logical conformance boundary rather than a runtime product, separates transport authentication from SAIF Authorization, keeps Provider and storage technology outside the core, and explicitly excludes commercial, payment, wallet, marketplace, and authentication-provider implementations.

The architecture is not yet precise enough for two independent implementations to produce interoperable behavior. The largest gaps occur where the draft moves from descriptive boundaries to state-changing protocol decisions:

1. Authorization evaluation has no portable decision artifact.
2. Required and optional extensions have no machine-readable declaration model.
3. atomicity, idempotency, and concurrency are described but not specified as observable requirements;
4. abstract API operations have ambiguous preconditions and postconditions; and
5. the security model defines principles without a minimum interoperable security profile.

The PR should remain Draft. No runtime implementation is required to resolve these findings; the required changes are specification artifacts, schemas, operation contracts, and conformance vectors.

## Review Criteria

The review applies the following tests:

- Can two independent implementations reach the same protocol decision from the same inputs?
- Can a caller distinguish transport success from protocol and business success?
- Can required behavior be tested using public conformance vectors?
- Can extensions be negotiated without redefining the core?
- Can storage technology vary while preserving the same observable consistency?
- Can the security properties be implemented without selecting a vendor or authentication provider?
- Can the proposed v0.3 changes comply with the repository’s own versioning rules?

## Critical Findings

### C-01: Authorization Evaluation Has No Portable Decision Contract

**Area:** Core Boundary, API Surface, Security

**Evidence:**

- [Authorization Evaluation](../reference-architecture.md#4-authorization-evaluation) requires an “auditable authorization outcome.”
- [Object Operations](../reference-architecture.md#object-operations) defines `EvaluateAuthorization` and `ConvertRequest` as separate operations.
- The architecture does not define the fields, validity, revision binding, expiry, or lifecycle of the evaluation result.

**Impact:**

Independent nodes can evaluate the same Authorization but produce incompatible outcomes or apply the result to different Request revisions. A valid decision may become stale after Owner revocation, scope modification, Agent suspension, or Request mutation. `ConvertRequest` has no normative input that proves which decision authorized the conversion.

This creates authorization substitution and time-of-check/time-of-use risk. It also prevents deterministic conformance testing.

**Required change:**

Define a portable Authorization Decision contract or Reference Node profile result containing at least:

- decision ID;
- SAIF version;
- Request ID and Request revision;
- Authorization ID and Authorization revision;
- Agent ID and Owner ID;
- decision value such as `ALLOW`, `DENY`, or `REQUIRES_ACTION`;
- evaluated scope and limit references;
- reason codes;
- evaluation time and optional expiry;
- correlation ID; and
- policy or profile identifier.

`ConvertRequest` must consume a valid decision reference and reject a stale, revoked, mismatched, or expired decision. The contract must remain identity-provider-neutral and must not embed commercial policy implementation.

### C-02: Extension Negotiation Cannot Be Implemented Interoperably

**Area:** Extension Boundary, Version Negotiation, Security

**Evidence:**

- [Extension Registry](../reference-architecture.md#extension-registry) lists logical registry content.
- [Unknown Extension Handling](../reference-architecture.md#unknown-extension-handling) requires unknown optional extensions to be ignorable and unknown required extensions to fail closed.
- The required extension declaration format and capability discovery object shape remain open design questions.

**Impact:**

An implementation cannot determine, from portable protocol data, whether an extension is required or optional, where its schema is located, which objects it affects, or which namespace authority owns it. Nodes may disagree on whether to accept the same message. A malicious or ambiguous registry entry could inject validation or dispatch behavior.

**Required change:**

Define a machine-readable Extension Declaration containing:

- collision-resistant extension identifier;
- namespace authority;
- extension version;
- SAIF compatibility range;
- `required` boolean;
- affected objects, operations, or Provider capabilities;
- schema or validation artifact identifier and integrity reference;
- proposal identifier and status for standardized extensions; and
- behavior when the extension is absent or unknown.

Specify where declarations appear in discovery and operation context, how duplicates and version conflicts are resolved, and which registry data is trusted. Add valid and invalid conformance vectors for optional ignore, required reject, namespace collision, and incompatible version behavior.

### C-03: Atomicity, Idempotency, and Concurrency Are Not Normative Enough

**Area:** Storage Abstraction, Lifecycle Coordinator, API Surface

**Evidence:**

- [Atomicity Expectations](../reference-architecture.md#atomicity-expectations) says an implementation “should” commit related state atomically or provide equivalent recovery.
- [API Response Rules](../reference-architecture.md#api-response-rules) requires idempotent state-changing operations.
- idempotency scope, retention, object revision, and optimistic concurrency remain open questions.

**Impact:**

Two conforming nodes may create different results under retry or concurrency. Examples include duplicate Orders, two conflicting terminal states, an Order without a converted Request, or a completed Execution without the corresponding fulfilled Order. A transport retry can become a second business commitment.

The problem is observable protocol behavior, not an internal database choice, so leaving it implementation-defined weakens interoperability.

**Required change:**

Specify transport-independent consistency invariants:

1. define the idempotency scope as actor, operation, target, and key;
2. require deterministic replay of the original result within a declared retention window;
3. define an object revision or precondition token outside or inside the operation envelope;
4. define a standard conflict error for stale revisions;
5. require one terminal outcome per object revision chain;
6. make Request conversion plus Order creation an atomic observable outcome; and
7. define a portable incomplete-operation or compensation outcome when atomic commit is impossible.

The specification must define outcomes, not SQL transactions, distributed locks, or a storage vendor.

### C-04: The Abstract API Surface Contains Ambiguous Semantics

**Area:** API Neutrality, Core Boundary

**Evidence:**

- `CreateRequest` may return either `DRAFT` or `SUBMITTED`.
- `EvaluateAuthorization` returns an unspecified outcome.
- `ConvertRequest` creates two related state changes without a defined request or response envelope.
- HTTP-style paths appear beside abstract operations, but the abstract contracts lack actor roles, pre-states, post-states, and required error outcomes.

**Impact:**

Bindings can implement materially different operations while using the same names. The illustrative HTTP mapping may become a de facto standard even though it is declared non-normative. MCP, message, and local bindings cannot demonstrate equivalence because there is no binding-neutral operation contract to map.

**Required change:**

For every state-changing abstract operation, define:

- authorized actor roles;
- required operation context;
- required object and revision references;
- allowed pre-state;
- successful post-state and created objects;
- idempotency behavior;
- synchronous or asynchronous result semantics;
- standard error categories and codes; and
- required Audit Events.

Split `CreateRequest` and `SubmitRequest`, or require an explicit requested initial transition. Keep HTTP mappings in a clearly non-normative binding appendix or separate binding draft. Provider-result operations must state that only an authorized Provider identity or delegated system role may invoke them.

### C-05: The Security Model Has No Minimum Interoperable Security Profile

**Area:** Security Model, Identity Boundary, Provider Boundary

**Evidence:**

- [Security Invariants](../reference-architecture.md#security-invariants) and the threat matrix identify appropriate goals.
- [Authentication Boundary](../reference-architecture.md#authentication-boundary) delegates authentication details to binding profiles.
- canonical serialization, minimum public-network security profiles, and several replay and concurrency details remain open.

**Impact:**

The model permits two implementations to claim the same Reference Node profile while providing significantly different protection against authorization revocation races, Provider callback spoofing, extension supply-chain attacks, audit disclosure, tenant crossover, or object tampering.

Authentication-provider neutrality does not require security-property neutrality. The protocol can define required properties without selecting credentials or vendors.

**Required change:**

Define a minimum Reference Node security profile covering:

- authenticated and integrity-protected transport for non-local bindings;
- binding between authenticated peer and Party, Agent, or Provider reference;
- Authorization freshness, revocation, and decision expiry checks;
- replay protection and idempotency enforcement;
- Provider result origin and correlation validation;
- tenant and Owner data-isolation requirements;
- extension manifest provenance and integrity verification;
- audit/error access control and data minimization;
- secret exclusion requirements; and
- downgrade-resistant version negotiation.

Cryptographic algorithms and authentication providers may remain profile-selectable. Security conformance vectors should verify observable accept/reject behavior.

## Boundary Review

### Core Boundary

**Assessment:** Directionally correct; not yet sufficiently contractual.

Strengths:

- clear separation of validation, identity reference resolution, Authorization, lifecycle, errors, and audit;
- explicit statement that identity resolution is not an identity provider;
- correct distinction between schema validity and semantic validity;
- Provider workflow internals remain outside the lifecycle core; and
- portable errors and Audit Events are first-class outputs.

Required clarification:

- define normative inputs and outputs for each core module;
- distinguish identity resolution facts from trust decisions;
- define Authorization Decision and Provider Result contracts;
- state whether Error Mapper and Audit Emitter are mandatory for every profile; and
- clarify whether Provider Dispatch is core orchestration or an adapter-boundary responsibility.

The current internal diagram places Provider Dispatch inside the node while the adapter table treats Provider Adapter as external. A conforming implementation needs one unambiguous ownership model: the core authorizes and emits a dispatch intent; the adapter performs Provider-specific transport.

### Extension Boundary

**Assessment:** Good policy boundary; missing portable declaration and trust mechanics.

Strengths:

- extensions cannot weaken core requirements;
- unknown required extensions fail closed;
- optional extensions are ignorable only when core meaning remains intact;
- private namespaces cannot claim core status; and
- SEP governance is correctly referenced.

Required clarification:

- extension envelope and discovery schema;
- namespace authority and collision rules;
- schema integrity and retrieval rules;
- conflict resolution when multiple versions are declared;
- standardized versus experimental extension trust; and
- conformance expectations for extension interactions.

### Storage Abstraction

**Assessment:** Technology-neutral and well layered; observable consistency remains underspecified.

Strengths:

- logical stores do not mandate one physical database;
- object, transition, audit, error, extension, and idempotency concerns are separated;
- cross-object traceability requirements are explicit;
- privacy and retention are acknowledged; and
- immutable versions, event sourcing, and transactional snapshots remain valid implementation choices.

Required clarification:

- normative revision and concurrency model;
- minimum idempotency retention declaration;
- behavior for partial cross-object writes;
- canonical or lossless retrieval semantics;
- audit ordering key and sequence behavior;
- deletion/anonymization effects on reference integrity; and
- minimum query behavior for object history.

“Canonical payload or equivalent lossless representation” is too broad for signing, hashing, equality, or cross-node transfer. Canonical serialization may remain deferred, but v0.3 must state which operations do not rely on canonical bytes until a profile is accepted.

### API Neutrality

**Assessment:** Correctly labels HTTP as illustrative; abstract semantics are incomplete.

Strengths:

- discovery does not imply authorization;
- transport success is separated from business success;
- asynchronous execution uses non-terminal states;
- operation context separates transport authentication from business objects; and
- Standard Errors and Audit Events are integrated.

Required clarification:

- binding-neutral operation envelopes;
- precondition and postcondition tables;
- actor-role constraints;
- pagination and continuation semantics for history and audit;
- concurrency and stale-write behavior;
- asynchronous result correlation; and
- required versus optional operations for a conformance profile.

Until these contracts exist, the HTTP paths should remain informative examples and must not be used as v0.3 conformance targets.

### Security Model

**Assessment:** Strong threat inventory; insufficiently testable.

Strengths:

- clear trust zones;
- explicit confused-deputy, replay, downgrade, extension, Provider, audit, and data-leakage threats;
- no mandated identity provider or cryptographic vendor;
- sensitive Provider data and credentials remain outside portable objects; and
- extension proposals require security review.

Required clarification:

- minimum mandatory security properties by binding profile;
- Authorization revocation and freshness behavior;
- Provider callback/result authentication semantics;
- extension artifact provenance;
- multi-Owner or tenant isolation;
- audit confidentiality and authorized query rules;
- object integrity and revision verification; and
- conformance vectors for negative security cases.

## Recommended Changes

### P0 — Required Before Draft PR Approval

1. Add a portable Authorization Decision contract and bind Request conversion to it.
2. Add an Extension Declaration and capability-discovery contract.
3. Define normative operation preconditions, postconditions, actor roles, idempotency, and concurrency outcomes.
4. Replace storage “should” language with observable consistency requirements or explicitly profile those requirements.
5. Define the minimum Reference Node security profile in provider-neutral terms.
6. Clarify Provider Dispatch ownership between core dispatch intent and Provider Adapter transport.
7. Add valid and invalid conformance vectors for each new required behavior.

### P1 — Required Before v0.3 Release Candidate

1. Define Provider Result and asynchronous correlation envelopes.
2. Define object revision and stale-write error semantics.
3. Define idempotency retention discovery and deterministic replay output.
4. Define audit ordering or sequence semantics per object and correlation ID.
5. Specify operation/profile discovery as a machine-readable object.
6. Move illustrative HTTP paths into a separate non-normative binding draft.
7. Document which requirements form the mandatory Reference Node conformance profile.

### P2 — Required Before v1.0

1. Standardize canonical serialization or explicitly scoped canonical digest profiles.
2. Publish at least one complete transport binding specification.
3. Publish independent implementation conformance reports.
4. Define compatibility and migration behavior for object revisions and accepted extensions.
5. Complete privacy, retention, and deletion profiles.
6. Resolve all security-critical open design questions.
7. Demonstrate interoperability across at least two independently developed implementations.

## Breaking Change Risks

The repository’s versioning strategy states that changed semantics, removed fields, changed lifecycle behavior, or new mandatory behavior are breaking changes. The following decisions should be made before v0.3 contracts are treated as stable.

| Risk | Why it may become breaking | Mitigation |
| --- | --- | --- |
| Mandatory Authorization Decision | Existing implementations may convert Requests directly from Authorization data. | Introduce as an explicitly versioned Reference Node profile contract before implementations claim v0.3 conformance. |
| Required object revision fields | Adding required fields to existing objects violates Minor-version compatibility. | Place revision and precondition data in a v0.3 operation envelope, or make object fields optional until the next Major version. |
| Extension declaration placement | Later moving declarations between metadata, object envelope, and transport context will break parsers and negotiation. | Standardize one declaration envelope before publishing extension conformance. |
| `CreateRequest` semantics | Choosing `DRAFT` versus `SUBMITTED` after implementations ship changes operation meaning. | Split operations or require explicit initial state now. |
| Idempotency scope | Changing key scope can create duplicate or incorrectly deduplicated commitments. | Define scope and retention discovery before binding drafts. |
| Canonical serialization | Later canonical byte rules may invalidate stored hashes or signatures. | Mark all current digests non-normative and version any future canonicalization profile. |
| Minimum security profile | Making transport integrity, replay, or revocation behavior mandatory later changes conformance. | Define required security properties before v0.3 conformance claims. |
| Provider result authority | Tightening who may record Execution results may reject previously accepted calls. | Define actor roles and Provider identity mapping in the v0.3 operation contracts. |

### Version Classification Risk

v0.3 is a Minor version under `MAJOR.MINOR.PATCH`, so it may add backward-compatible features but should not silently impose incompatible required behavior on v0.2 objects.

The project should choose one of these approaches:

1. define the Reference Node as a new optional v0.3 profile with its own operation envelopes and conformance claim; or
2. defer required changes to existing core object semantics to the next Major version.

The review recommends the first approach. It allows v0.3 to add architecture and binding profiles without retroactively changing the meaning of v0.2 objects.

| Security Model | 2/5 | Threat coverage is good; minimum mandatory and testable controls are missing. |
| Conformance | 2/5 | Governance exists, but the current vector set is too small for architecture conformance. |

**Overall readiness: 2.6/5 — not ready for v1.0.**

### What Is Ready

- the protocol’s legal and conceptual boundary;
- the core business object sequence;
- business-neutral lifecycle state names;
- public versioning and proposal governance;
- separation of SAIF semantics from MCP transport;
- initial Standard Error and Audit Event models; and
- a credible logical Reference Node decomposition.

### What Blocks v1.0

- no portable Authorization Decision;
- no operation envelope or object revision contract;
- no extension declaration and negotiation schema;
- no binding-neutral API precondition/postcondition specification;
- no minimum security profile;
- insufficient architecture-level conformance vectors;
- no canonicalization or scoped integrity profile; and
- no evidence from two independent conforming implementations.

### Maintainer Recommendation

Keep PR #1 in Draft and request specification changes. The architecture should be approved only after the P0 findings have explicit contracts and conformance coverage.

The project should not begin a normative runtime, commercial platform, payment implementation, or MCP Adapter as a substitute for resolving these specification gaps. Reference implementations may eventually provide evidence, but protocol meaning must remain fully defined by public documents, schemas, and vectors.

## Review Conclusion

Draft PR #1 establishes the right architecture shape and respects SAIF’s public-standard boundaries. Its primary weakness is not overreach; it is under-specification at the exact points where independent nodes must make the same state-changing decision.

The recommended path is to preserve the current modular structure, add portable decision and operation contracts, make consistency and security outcomes testable, and expand conformance vectors. With those changes, v0.3 can become a credible Reference Node profile without introducing runtime or commercial implementation dependencies.
