- **Decision:** **NOT READY TO FREEZE**

This review covers the public SAIF Protocol specification and its normative
conformance artifacts. It does not review, introduce, or require runtime code,
an MCP adapter, commerce behavior, payment logic, or a Provider-specific
implementation.

## Executive Summary

PR #4 resolves the five blockers from the
[freeze candidate review](v0.3-freeze-candidate-review.md):

- the BCP 14 declaration and normative scope are explicit;
- extension namespaces use one RFC 1035-compatible reverse-domain grammar;
- error locations use deterministic RFC 6901 JSON Pointers;
- Status Model, API actor, operation, query, discovery, and pagination vectors
  are present; and
- the coverage matrix accounts for all 66 published vectors.

Five of the six final approval checks pass, subject to the normal release-tag
gate. The candidate is nevertheless not ready to freeze because the published
coverage matrix does not provide deterministic evidence for every BCP 14
`MUST` and `MUST NOT` in the declared normative scope. Several uncovered
requirements are independently observable and are not declared as future
binding-only behavior.

This is a conformance-evidence blocker, not a protocol-design blocker. It can be
resolved without changing the object model, lifecycle, API design, runtime
boundary, or commercial scope.

## 1. MUST Requirement Conformance Evidence

### Result: Blocking

The [Normative Language](../normative-language.md) specification states that
every `MUST` or `MUST NOT` requires deterministic conformance evidence unless
the applicable profile explicitly states that the requirement cannot be tested
without a future binding.

The [v0.3 Reference Node Coverage
matrix](../conformance.md#v03-reference-node-coverage) maps 66 vector IDs into
20 broad requirement rows. All published vectors are represented, but the
matrix is vector-complete rather than clause-complete: it does not identify
every normative requirement and does not show evidence for the requirements
below.

### Blocking finding FA-01: Common operation context is not fully evidenced

[Action Execution Semantics](../specs/action-execution-semantics.md) requires
every state-changing operation to carry or resolve the complete operation
context, including operation ID, selected version and profile, correlation ID,
idempotency key, actor, target, Authorization Decision reference when
applicable, extension references, and payload.

`api-operation-matrix-010` demonstrates the required operation names,
pre-states, post-states, one allowed actor, idempotency key, result, and audit
reference. It does not contain or resolve the complete context for each row.
In particular, operation ID, correlation ID, target reference, applicable
Authorization Decision reference, extension references, and payload are absent.
No other matrix row claims this requirement.

**Required evidence:** add a valid complete-envelope vector and invalid vectors
for required context loss, or map existing vectors that explicitly contain and
target each invariant.

### Blocking finding FA-02: Idempotency retention is not evidenced

Action Execution Semantics requires a node to advertise
`idempotency_retention_seconds`, requires a minimum of 86,400 seconds, and
prohibits reuse or forgetting of a key before the advertised interval.

`api-discovery-behavior-013` proves that 86,400 seconds is advertised.
`action-semantics-valid-001` proves an unchanged replay. Neither vector proves
behavior at the retention boundary or that the key remains protected for the
entire advertised interval.

**Required evidence:** add deterministic recorded-time cases immediately before
the advertised expiry and, if post-expiry behavior is claimed, immediately
after it. No wall-clock runtime is required.

### Blocking finding FA-03: Extension safety and selection evidence is incomplete

[Extension Declaration](../specs/extension-declaration.md) requires a conforming
node to:

- compare semantic-version components numerically;
- record the selected manifest and digest in operation audit context;
- avoid executing code merely because a manifest contains a schema URI;
- prevent a schema URI from triggering unrestricted network access; and
- prevent extensions from weakening core validation, Authorization, lifecycle,
  error, or audit requirements.

The current compatibility vector compares `0.3.0` with `0.4.0`; that case has
the same result under numeric and lexical comparison. The discovery vector
exposes a verified digest but does not prove operation audit attribution. No
vector demonstrates the no-code-execution, restricted-retrieval, or
no-core-weakening requirements.

**Required evidence:** add a lexical-trap semantic-version case, an operation
audit case containing the selected manifest and digest, and observable safety
vectors whose expected result records no code execution, no unrestricted
network retrieval, and no weakened core decision.

### Blocking finding FA-04: Security-profile MUST evidence is incomplete

[Security Profile](../specs/security-profile.md) defines 13 required security
properties and additional BCP 14 requirements. The `SEC-01` matrix row covers
Owner isolation, Provider attribution, version negotiation and downgrade,
extension integrity, and secret redaction. It does not provide deterministic
evidence for at least:

- safe Standard Error behavior when binding-level resource limits are reached;
- append-oriented or equivalently tamper-evident Audit Event protection;
- bounded and authorized audit pagination as a security-profile behavior;
- retention and deletion behavior preserving minimization and accountability;
- documented extension-source trust policy; and
- identification of algorithms and downgrade behavior by a selected binding
  profile.

These requirements are not explicitly marked as untestable until a future
binding. Artifact inspection can satisfy documentation requirements; recorded
input/output vectors can satisfy observable outcomes. Neither form of evidence
is identified in the current matrix.

**Required evidence:** extend the coverage matrix to identify artifact or vector
evidence for each requirement. If a requirement genuinely belongs to a future
binding, record that deferral explicitly in the applicable profile before
claiming full v0.3 Reference Node conformance.

### Blocking finding FA-05: Provider and audit evidence is incomplete

Action Execution Semantics prohibits a Provider from creating or modifying
Owner Authorization, rewriting the original Request, or changing unrelated
objects. The Provider mismatch vector validates actor identity but does not
exercise these forbidden mutations.

The same specification requires Audit correlation to preserve operation ID,
protected idempotency reference, actor, object revisions and states,
Authorization Decision ID, Provider ID when applicable, and outcome or Standard
Error reference. Existing audit and replay vectors prove portions of this set,
but no vector or matrix row demonstrates the complete required correlation.

**Required evidence:** add one forbidden-Provider-mutation vector and one
complete action-to-audit correlation vector, plus invalid omissions where the
required value would otherwise be ambiguous.

### Coverage conclusion

The existing 66 vectors remain valid and materially improve interoperability.
The blocker is not their structural quality; it is the absence of a complete
normative-clause-to-evidence inventory. A release claiming that all v0.3
Reference Node `MUST` requirements are evidenced cannot be independently
reproduced from the current matrix.

## 2. Normative Definition Consistency

### Result: Pass

No conflicting normative definitions were found in the reviewed v0.3
specifications.

- Protocol Status is defined only by
  `schemas/common-status.schema.json`.
- Action Outcome is defined only by
  `schemas/action-outcome.schema.json`.
- Request, Order, Execution, and Settlement lifecycle states remain defined by
  the State Model and their object schemas.
- API results preserve Protocol Status, Action Outcome, and lifecycle state as
  separate layers.
- the Audit Event `outcome` is explicitly a backward-compatible projection,
  while `details.action_outcome` preserves the exact v0.3 Action Outcome.
- the core Standard Error registry assigns one category and meaning to each
  reserved code.

The normative dependency chain among Authorization Decisions, Action
Execution, API Operations, Extensions, Status, Errors, Audit Events, and the
Security Profile is internally consistent.

## 3. Schema Identity and Immutability

### Result: Pass with release-tag gate

All 12 schemas:

- declare JSON Schema Draft 2020-12;
- use a unique `$id`;
- use the exact immutable candidate form
  `https://raw.githubusercontent.com/songluyi/SAIF-Protocol/v0.3.0/schemas/<file>`;
  and
- declare `x-saif-version` as `0.3.0`.

Schemas that contain an instance-level `saif_version` constrain it to `0.3.0`.
This is consistent with the
[Protocol Versioning Strategy](../protocol-versioning.md).

The `v0.3.0` tag does not yet exist, which is valid for a pre-release candidate.
Freeze publication MUST create the tag at the finally approved commit and MUST
never move or reuse it. Until that tag exists, the canonical `$id` URLs are
identifiable but not yet resolvable release artifacts.

## 4. Extension Namespace Consistency

### Result: Pass

The proposal process, Extension Declaration, Extension Manifest schema, and
conformance vectors use the same namespace rule:

- lowercase reverse-domain identifiers;
- at least two RFC 1035-compatible labels;
- labels of 1 to 63 ASCII characters;
- a letter at the start and a letter or digit at the end of each label;
- lowercase letters, digits, and interior hyphens only;
- a maximum total length of 253 characters;
- `extension_id` beginning with `namespace + "."`; and
- reserved `org.saif` ownership for standard namespaces.

Valid and invalid vectors cover the accepted grammar, leading and trailing
hyphens, empty labels, leading digits, the reserved namespace, and namespace
prefix mismatch. No contradictory legacy `x-...` convention remains normative.

## 5. Deterministic Error Semantics

### Result: Pass

The Standard Error Model and Conformance Specification now agree that error
locations are RFC 6901 JSON Pointers relative to the complete input instance.
They define:

- the empty string as the root pointer;
- `/` as the member whose name is empty;
- mandatory `~0` and `~1` escaping;
- missing-member paths;
- smallest-responsible-value paths for semantic failures; and
- exact path comparison by conformance runners.

The vector envelope accepts the empty root pointer, invalid vectors use the
normalized error categories, and the primitive root-error vector uses the root
representation. The core error registry prevents a second normative meaning
from being assigned to an existing code.

## Non-Blocking Recommendations

1. Give each BCP 14 requirement a stable identifier and make the coverage
   matrix requirement-to-evidence complete, not only vector-complete.
2. Permit evidence types such as `VECTOR`, `SCHEMA`, and `ARTIFACT_AUDIT` so
   documentation-only and future-binding requirements are represented without
   pretending that all requirements are JSON-instance validations.
3. Publish a small release manifest containing the approved commit, tag,
   normative artifact paths, schema `$id` values, and vector digest set.
4. Keep future changes to a normative `MUST` and its conformance evidence in
   the same proposal or pull request.

## Final Freeze Decision

### NOT READY TO FREEZE

PR #4 should not be approved as the frozen SAIF Protocol v0.3.0 specification
in its current form. It resolves every blocker recorded in the preceding freeze
candidate review, and the protocol definitions are consistent, versioned, and
deterministic. However, FA-01 through FA-05 prevent the repository from
demonstrating its own repository-wide rule that every `MUST` and `MUST NOT` has
deterministic conformance evidence.

The next approval review should occur after the coverage inventory is
clause-complete and the missing evidence is added or explicitly deferred by the
applicable profile. This work requires specification tests and evidence only;
it does not require protocol redesign, runtime code, MCP implementation,
commerce integration, or payment logic.
