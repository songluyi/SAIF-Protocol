# SAIF Protocol v0.3 Freeze Candidate Review

## Review Status

- **Review target:** Draft PR #3, `Resolve SAIF Protocol v0.3 freeze blockers`
- **Head commit:** `0c88f7dccdd3b6d4268e48cf81b56db8ff819b15`
- **Base commit:** `4a05e42078d985369d1be37c3177b98772c877df`
- **Review date:** 2026-08-09
- **Review type:** freeze-candidate standards and conformance audit
- **Decision:** **NOT READY TO FREEZE**

This review covers the public protocol specification only. It does not review,
introduce, or require runtime code, an MCP adapter, commerce behavior, payment
logic, or a Provider-specific implementation.

## Executive Summary

PR #3 resolves the five blockers recorded in the previous freeze review at the
model level. Schema identities are uniformly versioned, the status vocabularies
are separated, extension governance now uses one reverse-domain convention, the
error taxonomy is normalized, and the conformance suite has grown from 13 to 48
vectors.

The candidate is nevertheless not ready to freeze. Five blocking issues remain:

1. the namespace schema accepts identifiers that do not conform to the stated
   reverse-domain convention;
2. the Status Model's own MUST-level conformance cases are not fully represented
   by countable vectors;
3. the required API operation and actor matrix is substantially uncovered;
4. the vector envelope does not define deterministic error-path semantics and
   cannot represent a root JSON Pointer; and
5. RFC-style normative keywords are used without a BCP 14 interpretation and
   scope rule.

These are protocol testability and interpretation blockers. No runtime or
commercial implementation is needed to resolve them.

## 1. Schema Identity Consistency Audit

### Result: Pass

All 12 files under `schemas/`:

- declare JSON Schema Draft 2020-12;
- declare `x-saif-version` as `0.3.0`;
- use a unique canonical `$id`; and
- use the same immutable-version form:

```text
https://raw.githubusercontent.com/songluyi/SAIF-Protocol/v0.3.0/schemas/<filename>
```

The audit found 12 unique `$id` values for 12 schemas. The Protocol Status and
Action Outcome enumerations occur only in
`schemas/common-status.schema.json` and
`schemas/action-outcome.schema.json`, respectively.

This is consistent with `docs/protocol-versioning.md`, which prohibits moving a
release tag referenced by a normative schema identity.

### Release condition

The identifiers become resolvable and immutable only when the reviewed content
is published under tag `v0.3.0`. The freeze/release procedure MUST create that
tag at the reviewed commit and MUST never retarget it. This is a release gate,
not a schema-design blocker in the candidate branch.

## 2. Status Model Consistency Audit

### Vocabulary result: Pass

`docs/specs/status-model.md` now separates:

- **Protocol Status:** `SUCCESS`, `PENDING`, `FAILURE`;
- **Action Outcome:** `APPLIED`, `REPLAYED`, `PENDING`, `REJECTED`, `CONFLICT`,
  `FAILED`; and
- **Action Lifecycle:** object-specific states from the State Model and object
  schemas.

The result envelope names Protocol Status and Action Outcome separately. The
Audit Event projection is explicitly lossy while preserving the exact Action
Outcome in `details.action_outcome`. This resolves the previous duplicate-status
semantic blocker.

### Blocking finding FC-01: Status MUST coverage is incomplete

The Status Model says conformance MUST verify:

- Protocol Status `SUCCESS` with every permitted Action Outcome;
- Protocol Status `FAILURE` with an error and no Action Outcome;
- the distinction among all three meanings of `PENDING`;
- every Audit Event projection while preserving the exact Action Outcome; and
- invalid values in both directions between Action Outcome and lifecycle fields.

The suite contains a valid `SUCCESS` plus `REJECTED` vector, a valid `FAILURE`
without Action Outcome vector, and one invalid lifecycle-as-outcome vector. It
does not provide countable coverage for all six Action Outcomes, the three
distinct `PENDING` meanings, the full Audit projection, or the inverse
outcome-as-lifecycle rejection.

Other action vectors contain outcome values, but the v0.3 Conformance
Specification permits shared credit only when a vector's description and target
identify the shared invariant. Those vectors do not identify these Status Model
invariants and therefore cannot deterministically satisfy its MUST list.

**Required freeze action:** add or explicitly map deterministic vectors for
every Status Model conformance bullet. A machine-readable coverage table may map
one vector to multiple requirements without executing it more than once.

## 3. Namespace Grammar Audit

### Governance alignment: Pass

`docs/proposal-process.md`, `docs/specs/extension-declaration.md`, the Extension
Manifest schema, examples, and current vectors now use one lowercase
reverse-domain convention. The extension identifier prefix relationship remains
an explicit semantic check, and an invalid namespace-prefix vector exercises it.

### Blocking finding FC-02: Schema accepts an invalid reverse-domain label

The Extension Manifest schema uses:

```regex
^[a-z][a-z0-9]*(\.[a-z0-9][a-z0-9-]*)+$
```

That pattern accepts `org.example-`. A label ending in a hyphen is not a valid
domain-name label, so an implementation applying the JSON Schema literally may
accept a manifest that an implementation applying the documented
reverse-domain rule rejects.

The documents do not define an alternative ABNF or state that the schema's
looser grammar overrides domain-name syntax. There is also no boundary vector
for leading/trailing hyphens, repeated dots, label count, case, or reserved
`org.saif` use.

**Required freeze action:** publish one exact namespace grammar, align the
schema pattern with it, and add boundary vectors. The semantic rule requiring
`extension_id` to begin with `namespace + "."` should remain separately tested.

## 4. Contract MUST Coverage Audit

### Coverage that is sufficient

The 48-vector suite now provides direct, reviewable evidence for the principal
MUST cases in these specifications:

- Authorization Decisions: all three decisions, expiry, revision binding,
  revocation, cross-Request replay, and non-`ALLOW` conversion;
- Extension Declarations: optional and required manifests, unknown behavior,
  compatibility, digest, duplicate conflict, namespace-prefix mismatch, and
  required/ignore rejection;
- Action Execution: unchanged and changed-input replay, stale revision,
  concurrent terminal conflict, atomic Request and Execution outcomes,
  asynchronous completion, Provider authority, and replay audit de-duplication;
  and
- Security Profile: Owner isolation, Provider attribution, downgrade rejection,
  extension integrity, idempotency conflict, and safe error/audit output.

### Blocking finding FC-03: Required API surface lacks its mandated matrix

`docs/specs/api-operation-semantics.md` requires vectors for actor roles,
every pre-state and successful post-state, stale revisions, replay,
Authorization freshness, Provider authority, atomicity, asynchronous outcomes,
required extensions, Standard Errors, and Audit Event references.

No vector targets the API Operation Semantics specification. More importantly,
no vector description identifies operation-level coverage for at least these
required operations:

- `CreateRequest`;
- `ConfirmOrder`;
- `CancelOrder`;
- `CreateExecution`;
- `StartExecution`;
- `FailExecution`;
- `CreateSettlement`;
- `Settle`; and
- `RefundSettlement`.

The suite also lacks a countable allowed/denied actor matrix for the required
state-changing, discovery, and query operations. Query authorization and
pagination behavior are not covered. Consequently, two implementations could
claim the same Reference Node profile while differing on required operation
preconditions and actor permissions.

**Required freeze action:** publish a requirement-to-vector coverage matrix and
add the missing operation, actor, discovery, query, and pagination vectors. If
any operation is intentionally outside v0.3 conformance, change its normative
status through governance before freeze rather than relying on implicit
deferral.

## 5. Vector Envelope Audit

### Structural result: Pass

- All 48 vectors parse as JSON.
- All 48 validate against
  `schemas/conformance-vector.schema.json`.
- Vector IDs are unique.
- Directory expectation and envelope expectation agree.
- Error categories use the normalized Standard Error taxonomy.
- The 12 vectors that directly target a JSON Schema produce their declared
  valid or invalid result.

### Blocking finding FC-04: Error paths are not interoperably defined

The envelope requires `expected_error.path`, but:

1. `docs/conformance.md` does not define whether it is a JSON Pointer, an
   operation-model path, or another notation;
2. the invalid-vector pass criteria compare category and code but do not compare
   the required path;
3. the schema pattern `^/` cannot represent the empty JSON Pointer for a root
   instance error; and
4. `status-lifecycle-as-action-outcome.json` targets a primitive schema with
   instance `"AUTHORIZED"`, whose validation error is at the root, while the
   vector declares `/action_outcome`.

This makes the required field non-deterministic and prevents independent vector
runners from agreeing on whether the same error location passes.

**Required freeze action:** define the path notation and comparison rule,
support its root representation, and correct the primitive-schema vector. If
logical protocol paths rather than instance-relative JSON Pointers are intended,
that rule must be stated and applied consistently to every vector.

## 6. RFC Normative Language Audit

### Blocking finding FC-05: BCP 14 interpretation and scope are undefined

The normative documents use uppercase `MUST`, `MUST NOT`, `SHOULD`, and `MAY`
extensively. Only `docs/reference-architecture.md` provides an informal note,
and it does not:

- cite RFC 2119 and RFC 8174;
- state that the keywords have special meaning only when shown in capitals;
- list the complete keyword set; or
- define whether the interpretation is inherited by every normative document,
  schema annotation, and conformance specification.

[RFC 8174](https://www.rfc-editor.org/rfc/rfc8174.html) requires an explicit
BCP 14 boilerplate when its uppercase keyword convention is used. The meanings
and intended use of the keywords originate in
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119.html).

Without a repository-wide interpretation rule, lowercase `must` and `may` in
the same documents can be read either as ordinary prose or as requirements,
and independent reviewers cannot classify them consistently.

**Required freeze action:** add one authoritative Normative Language section
using the RFC 8174 BCP 14 boilerplate and define its repository-wide scope, or
include the boilerplate in every normative specification. Then audit lowercase
requirement prose and capitalize only statements intended to be normative.

## Non-Blocking Recommendations

1. Publish a machine-readable conformance coverage manifest keyed by normative
   requirement and vector ID.
2. Add namespace boundary vectors even after the immediate grammar defect is
   corrected.
3. Record the release tag and schema digest set in the freeze record.
4. Keep requirement wording and conformance evidence in the same change when a
   future SEP adds a mandatory behavior.
5. Add a Markdown link and anchor checker to prevent normative dependency drift.

## v0.3 Freeze Decision

### NOT READY TO FREEZE

PR #3 should not yet be accepted as the frozen v0.3 specification. Schema
identity and the core status separation are sound, and the blocker-resolution
work is substantial, but FC-01 through FC-05 still allow incompatible
conformance claims or non-deterministic validation.

The next freeze review should occur only after:

1. Status Model MUST coverage is complete and countable;
2. the reverse-domain namespace grammar and boundary vectors agree;
3. the API operation and actor coverage matrix is complete or normatively
   narrowed through governance;
4. vector error-path semantics, root representation, and pass criteria are
   deterministic; and
5. BCP 14 keyword meaning and scope are explicit.

No runtime, MCP adapter, commerce implementation, payment implementation, or
commercial platform is required for any of these corrections.
