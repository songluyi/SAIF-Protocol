# SAIF Protocol v0.3 Standards Roadmap

## Objective

SAIF Protocol v0.3 will convert the v0.1 Business Object Model and v0.2 governance specifications into a reviewable, transport-independent Reference Architecture and a set of draft binding contracts.

The roadmap produces public standards artifacts only. It does not create a runtime, MCP Adapter, commercial platform, payment implementation, wallet, marketplace, or authentication provider.

## Starting Point

v0.3 builds on:

- the Party → Agent → Request → Authorization → Order → Execution → Settlement model;
- standard lifecycle states and transitions;
- explicit protocol versioning;
- conformance vector governance;
- extension proposal governance;
- the Standard Error Model;
- the Audit Event Model; and
- the SAIF/MCP responsibility boundary.

## Protocol Contract Hardening Milestone

The architecture review identified five interoperability gaps. v0.3 addresses them with the following public-standard artifacts:

| Review gap | Normative artifact | Status |
| --- | --- | --- |
| Portable authorization outcome | [Authorization Decision Contract](specs/authorization-decision-contract.md) and `schemas/authorization-decision.schema.json` | Draft complete |
| Machine-readable extension negotiation | [Extension Declaration](specs/extension-declaration.md) and `schemas/extension-manifest.schema.json` | Draft complete |
| Atomicity, idempotency, and concurrency | [Action Execution Semantics](specs/action-execution-semantics.md) | Draft complete |
| Neutral operation contracts | [API Operation Semantics](specs/api-operation-semantics.md) | Draft complete |
| Minimum security requirements | [Security Profile](specs/security-profile.md) | Draft complete |
| Status-layer separation | [Status Model](specs/status-model.md), `schemas/common-status.schema.json`, and `schemas/action-outcome.schema.json` | Draft complete |

These artifacts harden the logical architecture without adding runtime code, an MCP implementation, commerce behavior, or payment logic.

## Freeze Blocker Resolution Candidate

The final freeze review remains authoritative and v0.3 is **not frozen**. The
resolution candidate provides:

- immutable release-tag schema identities and `x-saif-version` annotations;
- separate Protocol Status, Action Outcome, and Action Lifecycle semantics;
- one reverse-domain extension namespace convention;
- a normalized conformance envelope and Standard Error taxonomy; and
- expanded Authorization, Action, Extension, and Security vectors.

These changes require a new freeze review before any v0.3 freeze decision.

## Workstream 1: Reference Architecture Review

### Goal

Reach consensus on the logical SAIF Reference Node and its normative boundaries.

### Deliverables

- Reference Node context and internal architecture;
- Core Module Boundary;
- Transport, identity, Provider, storage, and audit adapter boundaries;
- Extension Registry boundary;
- logical storage model;
- API surface draft; and
- security model draft.

### Review Questions

- Which modules are required for a conformance claim?
- Which responsibilities are normative and which are implementation choices?
- Can each boundary be implemented without a vendor dependency?
- Does the design preserve the MCP/SAIF separation?
- Can Provider systems remain independent of internal node architecture?

### Exit Criteria

- no unresolved contradiction with v0.1 or v0.2;
- all required boundaries have explicit responsibilities and exclusions;
- open questions are documented; and
- architecture review feedback is resolved or tracked through proposals.

## Workstream 2: Reference Node Profile

### Goal

Define observable behaviors for a conforming logical Reference Node without publishing runtime code.

### Deliverables

- version and capability discovery profile;
- object validation profile;
- authorization evaluation behavior;
- lifecycle transition behavior;
- Provider result intake behavior;
- error and audit output requirements;
- idempotency behavior; and
- extension negotiation behavior.

The binding-neutral operation and action semantics in `docs/specs/` are the source of truth for these behaviors.

### Exit Criteria

- every required behavior can be tested externally;
- no behavior depends on a deployment topology or language; and
- each requirement maps to at least one conformance vector.

Authorization Decision and Extension Manifest behavior MUST be testable both as JSON Schema constraints and as cross-object semantic rules.

## Workstream 3: Storage and Consistency Profile

### Goal

Define required observable persistence semantics while remaining database-neutral.

### Deliverables

- object and relationship retention rules;
- state history requirements;
- atomicity and partial-failure expectations;
- replay and idempotency semantics;
- audit ordering requirements;
- privacy and retention considerations; and
- recovery behavior for incomplete operations.

Revision and idempotency requirements are standardized as operation metadata so the v0.2 business-object schemas remain backward compatible.

### Exit Criteria

- linked objects can be reconstructed across the complete lifecycle;
- conflicting terminal states are prevented;
- replay cannot duplicate a business commitment; and
- storage requirements do not mandate SQL, NoSQL, blockchain, or a commercial service.

## Workstream 4: API Surface and Transport Binding Drafts

### Goal

Define transport-independent operations, then show how bindings may carry them without changing business semantics.

### Deliverables

- abstract operation catalog;
- operation inputs, outputs, and Standard Errors;
- correlation and idempotency rules;
- asynchronous operation semantics;
- HTTP-style illustrative mapping;
- MCP binding design constraints; and
- message transport design constraints.

The v0.3 contract set standardizes abstract operations only. Concrete HTTP, MCP, or message bindings remain separate future profiles.

### Exit Criteria

- the abstract operations work without HTTP or MCP;
- transport success is distinct from business success;
- binding-specific authentication remains distinct from Authorization; and
- no MCP Adapter or runtime implementation is added to the standard repository.

## Workstream 5: Security Review

### Goal

Establish minimum security invariants and profile requirements for independent implementations.

### Deliverables

- trust-boundary model;
- threat and mitigation matrix;
- authorization substitution and confused-deputy analysis;
- replay and downgrade protections;
- Provider trust requirements;
- extension security review checklist;
- audit integrity requirements; and
- data-minimization guidance.

The minimum requirements are collected in the provider-neutral `saif-reference-node-security/0.3` profile.

### Exit Criteria

- every normative state-changing operation has an authorization and replay control;
- unknown required extensions fail closed;
- sensitive transport or Provider data is excluded from portable objects; and
- security requirements remain authentication-provider-neutral.

## Workstream 6: Conformance Expansion

### Goal

Translate v0.3 architecture requirements into public, deterministic test vectors.

### Required Vector Areas

- supported and unsupported version negotiation;
- schema-valid but semantically invalid objects;
- valid and invalid lifecycle transitions;
- authorized and unauthorized Request conversion;
- duplicate operation replay;
- Provider result correlation;
- unknown optional extension handling;
- unknown required extension rejection;
- Standard Error shape and category;
- Audit Event attribution and state transition; and
- cross-object reference integrity.

### Exit Criteria

- each required Reference Node behavior has valid and invalid vectors;
- vectors use synthetic, vendor-neutral data;
- expected error codes are stable; and
- a conformance report format is documented.

## Proposed Review Sequence

```text
Reference Architecture Draft
          ↓
Public Architecture Review
          ↓
Reference Node Profile Draft
          ↓
Security and Storage Review
          ↓
Binding Drafts
          ↓
Conformance Vector Expansion
          ↓
v0.3 Release Candidate
```

## v0.3 Release Criteria

SAIF v0.3 should not be marked complete until:

1. the Reference Architecture is accepted through public review;
2. Core and Extension boundaries are unambiguous;
3. storage requirements are implementation-independent;
4. the API surface is expressed as abstract operations;
5. security invariants are documented;
6. binding drafts preserve SAIF/MCP separation;
7. required conformance vectors are published;
8. all normative artifacts declare compatible versions; and
9. no commercial or Provider-specific dependency is required;
10. all normative schemas validate under JSON Schema Draft 2020-12 and expose immutable versioned `$id` values;
11. valid and invalid vectors cover schema rules, stale revisions, idempotent replay, required-extension failure, and Provider attribution;
12. normative Markdown has valid local links and unambiguous requirement language; and
13. all unresolved architecture-review findings are closed or explicitly deferred through the proposal process.

## Deferred Beyond v0.3

- production runtime implementation;
- SDK standardization;
- certification authority or hosted conformance service;
- Provider marketplace or discovery economics;
- payment, wallet, or commercial platform logic;
- jurisdiction-specific compliance profiles; and
- v1.0 stability guarantees.

## Path to v1.0

After v0.3, the project should use implementation feedback and independent conformance reports to identify ambiguities. v1.0 should stabilize only the object, lifecycle, boundary, error, audit, extension, and binding semantics that have demonstrated cross-implementation interoperability.
